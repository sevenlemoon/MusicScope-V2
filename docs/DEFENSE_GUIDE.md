# MusicScope 答辩说明

## 用直白语言介绍系统

- **前端（Next.js、React、TypeScript）**：呈现页面、全局中英文切换、播放器和 Studio 四声部混音器。Node.js 是运行前端开发工具所需的环境，并不承担音频分离。
- **后端（Python、FastAPI）**：提供有类型约束的接口，处理账号连接、资料库、推荐、现场演出和 Studio 任务；浏览器不会持有来源会话。
- **PostgreSQL、SQLAlchemy、Alembic**：保存规范化音乐实体、归属关系、同步状态、画像、演出缓存和音频任务。Alembic 负责可重复的数据库结构升级。
- **Docker**：提供隔离的本地 PostgreSQL 服务。
- **来源适配层**：隔离网易云音乐及演出来源。一个来源暂不可用时，已保存的本地资料仍可查看。
- **规范化身份**：内部 UUID 与 `ExternalIdentity` 将来源 ID 映射到 MusicScope 实体，避免同一首歌在多个歌单中被误认为多首。
- **推荐画像**：依据已收藏曲目、歌单收录、艺人关系与合作证据计算亲和度和重新发现候选。它是可解释的确定性计算，不是大语言模型或神经网络推荐器，也不推断播放次数。
- **音频工作进程**：使用单独的 Python 环境运行第三方 Demucs 分离模型。Torch、NumPy 和 Demucs 不进入 FastAPI 环境；MusicScope 实现了上传、持久任务、结果验证、波形与混音播放的完整产品流程。
- **MPS**：PyTorch 在 Apple Silicon 上调用 Apple GPU 的计算后端；不可用时可回退至 CPU。MusicScope 没有发明 Demucs 或 MPS。
- **HTTP Range 与 Web Audio**：私有 FLAC 声部支持分段读取，四路声音经 Web Audio 同步播放，具有定位、增益、静音、独奏和主音量控制。

## 常见问题

**为什么使用 FastAPI？** Python 接口与来源接入、推荐计算和音频任务代码衔接直接；依赖注入和 OpenAPI 合约让边界易于验证。

**为什么不能让前端直接连接音乐来源？** 后端需要保护私密会话，并建立稳定的规范化身份、归属、分页、来源记录和离线可读的资料库。

**推荐依据是什么？** 已保存的资料库、亲和度、歌单共同出现、合作关系、重新发现信号和有限度的探索候选。没有虚构播放次数或心理人格。

**为什么有多个演出来源？** 单一来源的覆盖可能不完整。MusicScope 保留来源证明并隔离局部故障；零结果只表示当前可用来源未找到经验证的近期演出。

**为什么 Studio 不处理网易云播放流？** 播放与处理的权限边界不同。Studio 只接受用户主动选择、且有权处理的本地文件。

**音乐宇宙中的连线代表什么？** 共同歌单或规范化合作曲目提供的有限关系证据，权重由后端计算。

**连接会话如何保护？** 来源会话材料加密存于 `MusicConnectionSecret`，不进入公开接口或日志，并由服务端按用户归属限制读取。首次启动还会把随机生成的数据库密码和加密密钥保存在忽略版本控制的本机 `.env` 中。

**可以把系统直接开放到局域网或公网吗？** 不可以。当前版本只支持本机部署，数据库、API、网页和网易云辅助服务的主机端口只绑定 `127.0.0.1`。`X-MusicScope-User-ID` 只是本地开发/测试的用户选择，不是远程身份认证。远程或多人部署还需要真实认证、TLS/反向代理策略和重新审查威胁模型。

## 演示与环境边界

首次安装需 Docker Desktop、Python 3.12、`uv` 和项目要求的 Node.js 24.21.0。启动脚本会尝试从用户已有的 nvm 安装中启用该版本；它不会安装 nvm，也不会修改系统 Node。若机器没有 nvm，双击启动前仍需完成用户级运行环境准备。

首次使用 Demucs 时可能需要在 Git 之外的缓存中下载模型权重。无可信曲风元数据或完整聆听历史时，音乐宇宙不会生成推测性曲风或时间线。现场演出取决于当前可用来源，不能保证全球完整覆盖。
